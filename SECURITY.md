# Security Model

## Design principles

- **Local only.** No account, server, cloud sync, telemetry, or internet
  permission.
- **Least disclosure.** Secrets are never stored in plaintext; file contents are
  encrypted at rest; the UI reports degraded protection honestly.
- **Separate trust domains.** Main authentication, Personal Vault, and Intruder
  Vault use different credential verifiers, Keystore aliases, associated data,
  and directories.
- **Fail closed.** Expired authentication stages deny access. A failed lock
  surface sends the protected app home instead of exposing it.
- **No silent repair.** A corrupted vault index is reported, not replaced.

## Credentials

### PINs and patterns

- PIN: 4–8 digits.
- Volume pattern: 4–8 UP/DOWN volume-key presses.
- Secrets are never persisted. Only a salted verifier is stored:

| Parameter | Value |
| --- | --- |
| Algorithm | PBKDF2-HMAC-SHA256 |
| Key length | 256 bits |
| Salt | 16 random bytes |
| PIN iterations | 600,000 |
| Pattern iterations | 120,000 |
| Comparison | `MessageDigest.isEqual` (constant time) |
| Storage | Base64 salt, hash, and iteration count |

The iteration count is stored with each verifier, so it can be raised later
without invalidating existing credentials.

### Credential families

Each family has an independent verifier and failure budget:

- main PIN;
- main volume pattern;
- recovery PIN;
- recovery pattern;
- Personal Vault PIN;
- Intruder Vault PIN.

Vault PINs must not match the main PIN, recovery PIN, or the other vault PIN.

## Encryption at rest

### Android Keystore

`KeystoreCipher` uses:

| Property | Value |
| --- | --- |
| Keystore | `AndroidKeyStore` |
| Algorithm | AES-256-GCM |
| IV | 12 random bytes, generated by Keystore |
| Tag | 128 bits |
| Key export | Not exportable |
| Default alias | `nexo.v3.store` |

The protected-app list and security log use the default alias. Each vault has its
own alias:

- `nexo.vault.personal.v1`
- `nexo.vault.intruder.v1`

### Vault index

Each vault directory contains `index.v1.enc`, an AES-256-GCM encrypted JSON
envelope. Writes are atomic: write a temporary file, fsync, rename. A process
death cannot leave a truncated index.

Paths:

```text
<app files>/nexo_vault/personal/index.v1.enc
<app files>/nexo_vault/intruder/index.v1.enc
<app files>/nexo_vault/<kind>/<fileId>.nxf.enc
```

### Streaming file container (`NXLF` v1)

```text
header : "NXLF" | version:int | chunkSize:int | idLen:int | fileId:utf8
body   : repeated [ blobLen:int | IV(12) || AES-GCM ciphertext+tag ]
footer : end=-1:int | blobLen:int | encrypted FooterPayload
footer : "NXLF" | totalChunks:long | totalBytes:long | sha256:32 bytes
```

- Magic: `NXLF` (`0x4E584C46`).
- Version: 1.
- Default chunk size: 64 KiB (allowed 4 KiB–1 MiB).
- Chunk AAD: `${kindAad}|file|$fileId|chunk|$index`.
- Footer AAD: `${kindAad}|file|$fileId|footer`.
- Footer binds total chunks, total bytes, and the whole-file SHA-256.

Because each chunk is bound to its vault, file ID, and index, chunks cannot be
reordered or moved between files or vaults. A content change fails a chunk tag
or the footer digest.

### Vault isolation

The two vaults are independent by construction:

| Layer | Personal | Intruder |
| --- | --- | --- |
| Credential kind | `PERSONAL_VAULT_PIN` | `INTRUDER_VAULT_PIN` |
| Keystore alias | `nexo.vault.personal.v1` | `nexo.vault.intruder.v1` |
| AAD | `com.vinay.nexolock.vault.personal.v1` | `com.vinay.nexolock.vault.intruder.v1` |
| Directory | `nexo_vault/personal` | `nexo_vault/intruder` |

A PIN accepted by one vault cannot decrypt the other vault's index or
attachments, even if the same digits were somehow configured.

## Authentication session

One session is created per lock launch. It enforces the fixed sequence:

```text
decoy → biometric → volume pattern → master PIN
```

- Each stage owns a monotonic deadline based on `SystemClock.elapsedRealtime()`.
- Pattern and PIN deadlines are fixed when the stage opens and are never
  restarted by input.
- Decoy, pattern, and PIN expiry are terminal.
- Biometric success advances; failure or cancellation denies.
- Strict mode, when enabled in the persisted configuration, requires the PIN
  after biometric or pattern success.
- Recovery starts with the recovery PIN, then the recovery pattern if configured.

## Lockout

| Failures | Delay |
| --- | --- |
| 5 | 30 s |
| 8 | 5 min |
| 12 | 30 min |

Lockout state is local. Expired deadlines clear but the failure counter remains,
so the next failure escalates.

## App protection

- Accessibility events provide fast foreground detection.
- UsageStats polling is a documented fallback (2-second cadence, screen-on only).
- An overlay shield covers the app while the lock activity starts.
- A lock launch that never produces a surface is treated as a failure: the
  activity is finished, the shield is hidden, the event is logged, and the
  protected app is sent home.
- Screen-off clears the unlocked set.

## Vault sessions

- Unlock sessions last three minutes in memory.
- Leaving the app for 10 seconds or more, timeout, or process death re-locks the
  vault. A pending SAF picker or delete confirmation keeps it unlocked until the
  result returns.
- Decrypted previews and thumbnails are cleared on lock.
- Export writes to a user-selected SAF destination; the vault copy is unchanged.
- A partial export destination is deleted on failure or cancellation.

## Security log

- Each record is encrypted with AES-256-GCM and the default Keystore alias.
- Each record contains timestamp, type, method, message, and the SHA-256 of the
  previous record, forming a tamper-evident chain.
- The journal is bounded at 2,000 records; when it exceeds that, the oldest
  records are trimmed to the most recent 1,000.
- Clearing the log writes a `LOG_CLEARED` event.

## Backup and data extraction

- `android:allowBackup="false"`.
- `android:fullBackupContent="false"`.
- Explicit data-extraction rules exclude app data.
- Cleartext traffic is disabled (`usesCleartextTraffic="false"`).
- No `INTERNET` permission is declared.

## Threat model

### Protected against

- Casual device access without the PIN/pattern.
- Offline inspection of app-private storage (index and files are encrypted).
- Chunk reordering or cross-vault file substitution (AAD binding).
- Silent vault corruption (authentication failure and SHA-256 verification).
- Credential reuse across vaults (explicit duplicate rejection).
- Brute-force guessing at the UI (progressive lockout).
- Screenshot leakage of vault/viewer routes (`FLAG_SECURE`).

### Not protected against

- A rooted or compromised device with active malware and unlocked Keystore.
- A malicious accessibility service or OS-level screen capture.
- Shoulder surfing, camera observation, or a compromised camera.
- Forensic attacks against a weak 4-digit PIN; PBKDF2 slows guessing but does not
  make a weak secret strong.
- App-launch interception guarantees; Android does not provide one.
- Data loss if the user forgets every credential. There is no cloud recovery.
- A compromised build signed with the same debug key.
